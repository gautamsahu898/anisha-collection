# Anisha Collection

Anisha Collection is a small self-hostable commerce application. It includes a responsive customer storefront, product catalogue, registration and login, server-side metre-based cart pricing and stock reservation, customer order history, and a password-protected admin area for products, customer records, inventory visibility, and order/payment status.

The storefront no longer inserts a prefilled catalogue or fabricated sales activity. Add the fabrics you actually sell in Studio; hidden starter entries remain unpublished so any earlier order history stays intact.

## Start locally

Requires Node.js 22.5 or newer (the server uses the built-in `node:sqlite`; Node may print its experimental warning). No npm dependencies are required.

1. Copy `.env.example` to `.env`.
2. Open `/admin.html` on the same computer and create an administrator account on the one-time localhost setup screen. Or set `ADMIN_EMAIL` and a long, unique `ADMIN_PASSWORD` before the first run to create it from the environment.
3. Set a verified merchant VPA in Admin → Payment settings before enabling checkout. The `.env` example leaves the UPI ID blank to prevent payments from being routed to a sample recipient. The payee name is the display name shown by the UPI app.
4. Start with `node --env-file=.env server.mjs`.
5. Open `http://localhost:3000`. Admin sign-in is at `/admin.html`.

The application creates `anisha.sqlite` beside the server on first run. Keep this file private and back it up. Do not put `.env` or the database in a public web directory or commit real secrets.

## Reset an administrator password locally

From a terminal in this project folder, run `node reset-admin-password.mjs`. Enter the admin email, type `RESET` to confirm, then enter and repeat a new password of at least 12 characters. Password input is hidden. The script updates only that local admin account, invalidates its existing sessions, and never prints or stores the new password in plaintext. Run it on the same computer and against the same `anisha.sqlite` database used by the server.

### Reset with an email code

On `/admin.html`, choose **Forgot password? Send me a code** and enter the administrator email. The code expires in 10 minutes and is limited to five attempts. Email reset is restricted to the computer running the local store server. To enable delivery, set `SMTP_USER` and `SMTP_FROM` to the Gmail address and `SMTP_APP_PASSWORD` to a Google app password in your private `.env`, then restart the server. Set `SMTP_HOST=smtp.gmail.com` and `SMTP_PORT=465`. Google app passwords require 2-Step Verification; create one in your [Google Account](https://support.google.com/mail/answer/185833?hl=en). Never use your regular Gmail password here or paste SMTP credentials into chat.

## Direct UPI payment behavior

Checkout calculates the final amount on the server, creates an order reference, reserves the requested stock, and produces a UPI payment URI containing the merchant VPA, exact amount, order reference, and INR currency. Customers can open a supported UPI app or scan the QR shown at checkout. After the transfer, the customer can mark the payment as submitted. This only changes the order to `payment_review`; it does not mark it paid. An administrator must check the actual merchant bank account and explicitly confirm receipt in Studio before the order becomes paid/confirmed.

This direct VPA/UPI URI flow has **no payment-provider callback**. Payment completion and refunds cannot be verified automatically, payment failures are not reported to this website, and a customer action or screenshot is not proof of payment. Never store or request a UPI PIN or OTP. The dynamic QR image is generated by a third-party QR rendering service and encodes the UPI URI; for production privacy, host an audited QR encoder yourself.

## Admin features

The admin dashboard requires an account with the `admin` role. It shows live totals and low-stock products, supports adding and publishing/unpublishing fabrics, lists customers and orders, permits order status updates, and has a manual UPI receipt confirmation action. Admin product image input currently accepts an image URL; secure multi-image upload and reordering need a configured private object-storage provider.

## Production readiness

This is a working local full-stack foundation, but it is not yet a hardened production deployment. Before collecting real customer information, add HTTPS and a deployment model that persists SQLite safely (or migrate to managed PostgreSQL), request rate limiting and account recovery, CSRF/origin protections, email verification/notifications, privacy/retention controls, shipping/tax rules reviewed for your business, returns/refunds workflows, stock release for abandoned/unpaid orders, image uploads with file validation, and operational backups/monitoring. The current stock reservation has no expiry job; unpaid orders hold their stock until an admin cancels the order. Review applicable Indian tax, consumer, privacy, and payment requirements for the business before launch.

## API overview

- `GET /api/products` — published catalogue.
- `POST /api/register`, `POST /api/login`, `POST /api/logout`, `GET /api/me` — customer/admin sessions.
- `POST /api/checkout`, `GET /api/orders`, `POST /api/orders/:id/payment` — own-account checkout, orders, and payment-submitted status.
- `GET /api/admin/summary`, `/api/admin/products`, `/api/admin/orders`, `/api/admin/customers` — admin-only dashboard data.
- `POST /api/admin/products`, `PUT|DELETE /api/admin/products/:id`, `PATCH /api/admin/orders/:id` — admin-only catalogue and order operations.

## Deploy a separate test store (Render)

The app uses SQLite, a real relational database stored in `anisha.sqlite`. For an online test, the included [`render.yaml`](render.yaml) mounts a persistent disk at `/opt/render/project/src/storage` and points `DATA_DIR` there, so test products, accounts, and orders survive restarts and deploys. Keep one service instance because SQLite uses a single local database file. The test service starts with a fresh database; your local customers and orders are not copied.

1. Push this project to a **private GitHub repository**. The `.gitignore` excludes `.env` and the SQLite files; never commit either or put credentials in GitHub.
2. In Render, select **New → Blueprint**, connect the repository, and review the service configuration from `render.yaml`.
3. Provide `ADMIN_EMAIL` and a unique `ADMIN_PASSWORD` of at least 12 characters in Render's private environment prompt. These create the first administrator for the new test database. Do not reuse a production password.
4. Apply the Blueprint and wait for the deploy to finish. Open the generated `onrender.com` URL and sign in at `/admin.html`.
5. The test store has no merchant UPI ID by default, so checkout stays disabled until you intentionally configure a test VPA in Admin → Payment settings. This direct UPI flow has no payment-provider sandbox or automatic payment verification.

This configuration uses Render's `0.5c-512mb` paid web service plan and a 1 GB persistent disk. Current listed pricing is approximately **$7/month for the service plus $0.25/month for the disk**, before taxes or additional usage. Render's free web filesystem is ephemeral and cannot provide this SQLite persistence. See [Render pricing](https://render.com/pricing), [Blueprint configuration](https://render.com/docs/blueprint-spec), and [persistent disk limits](https://render.com/docs/disks). Render services get a public URL; deployment makes this test storefront internet-accessible. Use test-only data until you're ready for a security and operations review.
